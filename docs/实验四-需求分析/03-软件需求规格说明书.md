## 1. 引言

### 1.1 编写目的

本文档依据《软件工程》实验四的要求,对居家养老系统进行完整的需求分析与建模。文档明确了系统的利益相关方、功能需求、非功能需求与外部接口需求,为后续软件体系结构设计、详细设计与测试验收提供依据。

### 1.2 项目背景

我国已进入中度老龄化社会,绝大多数老年人选择居家养老。空巢、独居老人普遍面临三大问题:健康状态无人持续监测、突发意外难以被及时发现、上门照护服务预约繁琐且质量参差。本系统面向居家养老场景,为老人提供一键呼救、健康监测、上门服务预约等服务,为家属提供远程看护能力,为护工提供接单平台,形成"老人—家属—护工—平台"四方协同的居家养老服务体系。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 老人 | 系统服务对象,60 岁及以上居家养老人群 |
| 家属 | 老人的直系亲属或监护人,可绑定老人账号并远程看护 |
| 护工 | 通过平台资质审核的上门服务人员 |
| SOS 呼救 | 老人触发的一键紧急求助,系统向家属与平台推送告警 |
| 可穿戴设备 | 具备心率/血压/血氧监测能力并能联网上报数据的智能设备 |
| 订单 | 老人或家属发起的一次上门服务预约及履约记录 |

## 2. 总体描述

### 2.1 产品前景

本系统为面向居家养老领域的综合性服务平台,应用终端覆盖**手机 APP(老人端/家属端/护工端)与网页管理端**。产品定位为:解决居家养老场景下"安全监护"与"照护服务"两大核心问题,先期在广州市部分社区试点运营,后续向更多城市复制推广。

### 2.2 产品功能概述

| 模块 | 功能概述 | 使用终端 |
|------|----------|----------|
| 用户中心 | 四类角色注册登录、实名认证、资料维护、老人-家属绑定 | APP + 网页端 |
| 安全监护 | 一键 SOS 呼救、健康数据监测、异常告警推送 | APP(老人端) |
| 服务预约 | 服务项目浏览、预约下单、在线支付、订单跟踪、服务评价 | APP |
| 护工工作台 | 接单、服务签到、凭证上传、收入结算查看 | APP(护工端) |
| 远程看护 | 绑定老人健康数据/位置/服务记录查看、告警接收 | APP(家属端) |
| 平台管理 | 用户管理、护工资质审核、服务类型管理、订单监管、数据统计 | 网页管理端 |

### 2.3 用户特征

| 用户群 | 特征 | 设计约束 |
|--------|------|----------|
| 老人 | 年龄大,视力/听力下降,智能手机操作能力弱 | 大字体、高对比度、一键式操作、语音播报 |
| 家属 | 中年人群,智能手机使用熟练,关注信息及时性 | 信息推送及时、操作路径短 |
| 护工 | 文化程度不一,移动办公场景 | 界面简洁、流程固定、弱网可用 |
| 平台管理员 | 具备一定计算机操作能力 | 后台功能完备、数据可导出 |

### 2.4 运行环境

- 服务端:Linux 服务器,Java 17 + Spring Boot 3.x + MySQL 8.0 + Redis;
- 客户端:Android 9.0 及以上、iOS 13.0 及以上;
- 网页管理端:Chrome / Edge 浏览器。

### 2.5 约束与假设

**约束**:
1. 老人端 APP 必须支持大字体与语音播报等适老化特性;
2. 支付功能必须对接持牌第三方支付平台(微信支付/支付宝),平台不自建支付;
3. 健康与位置数据属于个人敏感信息,采集与展示须符合《个人信息保护法》要求;
4. 开发周期为一学期,采用增量开发,核心功能(呼救+预约)优先交付。

**假设**:
1. 老人或家属持有智能手机且能接入网络;
2. 可穿戴设备厂商提供标准数据上报接口;
3. 服务人员具备真实资质,可由平台线下核验。

## 3. 功能需求

> 需求编号规则:FR-XX;优先级:高/中/低。输入/处理/输出按用例主流程描述。

### FR-01 用户注册与登录(优先级:高)

- **描述**:老人、家属、护工、管理员四类角色注册与登录。
- **输入**:手机号、验证码(注册);账号、密码(登录)。
- **处理**:
  1. 注册时校验手机号唯一性与验证码正确性,老人账号须填写紧急联系人;
  2. 密码采用 BCrypt 加密后存储;
  3. 登录成功返回角色令牌(Token),按角色跳转对应端界面;
  4. 老人端支持"家属协助登录"模式。
- **输出**:登录态 Token;失败时给出明确提示(手机号已注册、验证码错误等)。
- **对应用例**:UC01。

### FR-02 紧急呼救 SOS(优先级:高)

- **描述**:老人一键触发紧急呼救,系统实时通知绑定家属与平台。
- **输入**:老人触发呼救动作,APP 自动附带当前 GPS 位置。
- **处理**:
  1. 校验老人账号及其绑定家属关系;
  2. 生成告警记录(时间、位置、状态=未处理);
  3. 向全部绑定家属推送 APP 通知并发送短信,向平台监控后台推送提醒;
  4. 返回受理回执,APP 语音播报"呼救已发出"。
- **输出**:告警记录;家属端告警详情(老人位置、联系方式);管理员可更新处理状态。
- **性能要求**:端到端推送 ≤ 3s。
- **对应用例**:UC02、UC10。

### FR-03 健康数据监测(优先级:高)

- **描述**:接收可穿戴设备上报的健康数据,生成趋势记录,异常自动告警。
- **输入**:设备上报的心率、血压、血氧及测量时间。
- **处理**:
  1. 数据校验(范围合法性、设备绑定关系);
  2. 入库并按日/周生成趋势;
  3. 指标超出医学阈值(如静息心率 >120 次/分、血氧 <90%)时触发异常告警,通知家属;
  4. 家属端与老人端均可查看历史趋势。
- **输出**:健康趋势图;异常告警通知。
- **性能要求**:数据上报延迟 ≤ 5s。
- **对应用例**:UC03。

### FR-04 上门服务预约(优先级:高)

- **描述**:老人或家属选择服务项目(助餐、助洁、助浴、陪诊、家政)、服务时间与护工,提交预约。
- **输入**:服务类型、服务时间、服务地址、期望护工(可选)。
- **处理**:
  1. 校验家属与老人的绑定关系(家属代预约时);
  2. 查询该时间段可服务护工列表,按评分/距离/空闲排序;
  3. 生成"待支付"订单。
- **输出**:订单号及支付信息。
- **对应用例**:UC04。

### FR-05 服务订单管理(优先级:高)

- **描述**:订单从下单到评价的全生命周期管理。
- **输入**:支付结果回调、护工接单/完成操作、用户确认/取消操作。
- **处理**:订单状态按状态图流转(待支付 → 待接单 → 服务中 → 待确认 → 已完成 → 已评价,含各环节取消/退款分支);支付回调幂等处理。
- **输出**:各状态变更均向相关方推送通知;取消订单按规则退款。
- **对应用例**:UC05、UC06;状态转换见《UML 模型集》状态图。

### FR-06 家属远程看护(优先级:高)

- **描述**:家属绑定老人后,可远程查看老人健康数据、实时位置、服务记录,接收告警。
- **输入**:绑定老人(老人手机号+验证确认)。
- **处理**:建立绑定关系;看护页聚合展示老人健康趋势、最近位置、进行中订单。
- **输出**:看护首页数据;告警实时推送。
- **对应用例**:UC08、UC09。

### FR-07 服务评价(优先级:中)

- **描述**:服务完成后,下单人对护工进行 1~5 星评分与文字评价。
- **处理**:仅"已完成"订单可评价;评价结果参与护工排序与信用体系;敏感词过滤。
- **对应用例**:UC07。

### FR-08 消息通知(优先级:中)

- **描述**:关键事件(告警、订单状态变更、支付结果)通过 APP 推送与短信通知相关用户。
- **处理**:按事件类型选择通道:告警类双通道,普通订单通知仅 APP 推送;用户可设置免打扰时段(告警类除外)。
- **对应用例**:UC10。

### FR-09 护工工作台(优先级:高)

- **描述**:护工接单、服务签到、凭证上传、完成确认、收入查看。
- **输入**:接单确认、服务开始签到、服务凭证照片。
- **处理**:接单后展示老人地址与联系方式;服务开始/结束均需签到留痕;完成后须上传服务凭证,经用户确认后结算。
- **对应用例**:UC06。

### FR-10 平台后台管理(优先级:高)

- **描述**:平台管理员对系统进行管理与监管。
- **子功能**:
  - FR-10.1 用户管理:查询、冻结/解冻用户账号;
  - FR-10.2 护工资质审核:审核护工提交的资质材料(健康证、技能证书),通过后方可接单;
  - FR-10.3 服务类型管理:维护服务项目目录与定价;
  - FR-10.4 订单监管:查看全部订单,处理纠纷与退款;
  - FR-10.5 数据统计:用户数、订单量、GMV、告警处理时效等报表。
- **对应用例**:UC11~UC14。

### FR-11 在线问诊(优先级:低,二期)

- **描述**:对接医疗机构提供图文问诊入口。本期仅预留接口,不做实现。

## 4. 非功能需求

| 编号 | 类别 | 需求描述 |
|------|------|----------|
| NFR-01 | 性能 | 普通页面响应时间 ≤ 2s;SOS 告警端到端推送 ≤ 3s;健康数据上报入库延迟 ≤ 5s;系统支持 500 用户并发访问 |
| NFR-02 | 兼容性 | 支持 Android 9.0+、iOS 13.0+;网页管理端兼容 Chrome/Edge 最新两个大版本 |
| NFR-03 | 安全性 | 密码 BCrypt 加密存储;全链路 HTTPS;健康/位置等敏感信息展示时脱敏;基于角色的权限控制(老人不可见他人数据);接口防越权校验 |
| NFR-04 | 易用性 | 老人端支持大字体模式、语音播报、一键式操作;核心功能(呼救)1 步可达;整体核心操作 ≤ 3 步 |
| NFR-05 | 可用性 | 系统 7×24 小时运行,SOS 模块可用性 ≥ 99.9%;数据库每日备份 |
| NFR-06 | 可维护性 | 前后端分离、模块化分层架构;核心接口预留第三方对接扩展点;代码规范统一(注释率 ≥ 30%) |
| NFR-07 | 隐私合规 | 采集健康/位置数据须获得用户明示授权,提供注销账号与数据删除功能 |

## 5. 外部接口需求

| 接口 | 对接系统 | 交互内容 | 交互方式 |
|------|----------|----------|----------|
| IF-01 支付接口 | 微信支付/支付宝 | 下单支付、支付结果回调、退款 | HTTPS REST + 异步回调(幂等) |
| IF-02 设备数据接口 | 可穿戴设备厂商平台 | 心率/血压/血氧数据上报 | HTTPS 推送/MQTT,厂商标准协议 |
| IF-03 短信接口 | 第三方短信服务商 | 告警短信、验证码 | HTTPS REST |
| IF-04 推送接口 | 手机厂商推送通道(APNs/厂商通道) | APP 消息推送 | 各厂商 SDK |
| IF-05 问诊接口(预留) | 医疗机构平台 | 图文问诊(二期) | HTTPS REST |

## 7. 需求评审记录(摘要)

| 评审项 | 评审结论 |
|--------|----------|
| 规范性 | UML 模型元素完整、命名规范;需求条目采用统一编号格式 |
| 正确性 | 需求与实验一调研报告、实验二解决方案文档一致,无矛盾 |
| 一致性 | 用例图、顺序图、类图、状态图之间对象与流程一致 |
| 可理解性 | 需求描述无歧义,量化指标明确 |
| 可落地性 | 技术栈成熟(Spring Boot + MySQL + 微信/支付宝 SDK),具备落地条件 |

**主要评审意见及修改记录**:

1. 意见:"智能家居联动"需求与核心目标关联弱 → 处理:删除该需求,见《利益相关方与初步需求分析表》第 5 节;
2. 意见:订单完成缺少用户确认环节,存在纠纷风险 → 处理:状态图增加"待确认"状态,7 天未确认自动完成;
3. 意见:非功能需求缺少具体数值 → 处理:全部量化(≤2s、≤3s、Android 9.0+ 等);
4. 意见:健康数据属于敏感信息 → 处理:增加 NFR-07 隐私合规要求与脱敏展示要求。

完整评审记录见《04-需求评审记录.md》。
