**项目名称**:居家养老系统
**建模工具**:PlantUML(源码见 `uml/` 目录,可导出 PNG/SVG 图片)
**模型清单**:初步用例图 → 顺序图(2 个核心用例)→ 分析类图 → 状态图(服务订单)

---

## 0. 模型渲染方法(重要)

本模型集以 PlantUML 源码形式提供(`.puml` 文件),渲染成图片的三种方式任选:

1. **在线渲染(最简单)**:打开 <https://www.plantuml.com/plantuml/uml/>,把 `.puml` 文件内容粘贴进去,即可在线生成并导出 PNG 图片;
2. **IDEA 插件**:在 IntelliJ IDEA 中安装 *PlantUML Integration* 插件,直接打开 `.puml` 文件即可预览并导出图片(需 JDK,IDEA 自带);
3. **VSCode 插件**:安装 *PlantUML* 扩展,按 `Alt+D` 预览,右键导出图片。

> 导出图片后,建议截图或直接插入报告册"实验数据及结果"栏目中。

## 2. 交互图(顺序图,2 个核心用例)

### 2.1 紧急呼救(`uml/顺序图-紧急呼救.puml`)

**用例目标**:老人遇险一键求助,家属与平台第一时间获知。

**消息流**:
1. 老人点击"一键呼救"按钮(APP 首页常驻大按钮,适老化设计);
2. APP 携带老人 ID 与 GPS 定位向服务器发送 SOS 请求;
3. 服务器校验账号与绑定关系,生成告警记录(时间/位置/状态);
4. 服务器同时向绑定家属推送 APP 通知+短信、向平台监控后台推送提醒;
5. 返回受理回执,APP 界面语音播报"呼救已发出";
6. 家属查看告警详情(位置、联系方式),管理员核实并更新处理状态。

**关键设计点**:告警采用双通道(APP 推送+短信)保证送达;端到端推送时延 ≤ 3s(对应 NFR-01)。

### 2.2 上门服务预约(`uml/顺序图-服务预约.puml`)

**用例目标**:家属代老人预约上门照护服务并完成支付,护工接单。

**消息流**:
1. 家属选择服务类型(助餐/助洁/陪诊等)与服务时间;
2. 系统返回可服务护工列表(按评分、距离、空闲时段排序);
3. 提交预约订单,服务器校验后生成"待支付"订单;
4. APP 发起支付,支付平台回调支付结果;
5. 订单置为"待接单",向护工推送新订单通知;
6. 护工确认接单,订单置为"服务中",家属收到"护工已接单"通知。

**关键设计点**:支付回调幂等处理(防止重复回调造成重复扣款);护工接单采用推送+抢单机制。

## 3. 分析类图(`uml/分析类图.puml`)

### 3.1 类职责说明

| 类名 | 类型 | 核心属性 | 核心职责 |
|------|------|----------|----------|
| User | 基类(抽象) | userId, username, password, phone, role | 统一身份认证,四类角色继承 |
| Elder | 实体类 | name, address, emergencyContact | 老人档案;触发呼救、查看健康数据 |
| FamilyMember | 实体类 | name, relationship | 绑定老人、远程看护、代下单 |
| CareWorker | 实体类 | serviceTypes, qualificationStatus, rating, workStatus | 接单、完成服务 |
| Admin | 实体类 | name, dept | 审核资质、管理用户、统计 |
| ServiceType | 实体类 | typeName, price, description | 服务项目目录 |
| ServiceOrder | 核心实体类 | orderStatus, serviceTime, amount, payTime | 订单全生命周期 |
| HealthData | 实体类 | heartRate, bloodPressure, bloodOxygen, measureTime | 健康数据记录与异常判断 |
| SosAlert | 实体类 | alertTime, longitude, latitude, handleStatus | 告警记录与通知 |
| Review | 实体类 | score, content | 服务评价 |
| Notification | 实体类 | type, content, readFlag | 站内通知 |

### 3.2 主要关系

- **继承**:Elder / FamilyMember / CareWorker / Admin 继承 User(角色差异化);
- **关联(多对多)**:FamilyMember 与 Elder 绑定关系(一个家属可绑定多位老人,一位老人可被多位家属绑定);
- **聚合(一对多)**:Elder 拥有多条 HealthData / SosAlert / ServiceOrder;
- **关联**:ServiceOrder 属于某一 ServiceType、由某 CareWorker 服务、获得至多一条 Review;Notification 发送给 User。

## 4. 状态图(`uml/状态图-服务订单.puml`)

### 4.1 订单状态转换说明

| 当前状态 | 触发事件 | 目标状态 |
|----------|----------|----------|
| 待支付 | 支付成功(支付平台回调) | 待接单 |
| 待支付 | 超时 30 分钟未支付 / 用户取消 | 已取消 |
| 待接单 | 护工确认接单 | 服务中 |
| 待接单 | 用户取消并退款 / 超时无人接单 | 已取消 |
| 服务中 | 护工提交完成并上传凭证 | 待确认 |
| 服务中 | 服务异常终止(平台介入) | 已取消(退款) |
| 待确认 | 用户确认完成(超 7 天自动确认) | 已完成 |
| 已完成 | 用户提交评价 | 已评价(终态) |
| 已取消 | — | 终态 |

### 4.2 状态图与需求的一致性

状态图覆盖 FR-05 服务订单管理的全部状态流转,其中"待确认"状态的设计来源于订单纠纷场景(用户对服务结果存疑时可暂不确认,由平台介入),与 UC06 接单与完成服务、UC07 服务评价的用例流程一致。
